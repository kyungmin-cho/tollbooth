# M1 local feasibility spike

The owner authorized local implementation and sandbox order preparation on 2026-10-18. This note records the implemented subset of [PLAN](PLAN.md), not completion of M2–M6. The financial invariants in [DESIGN](DESIGN.md) remain unchanged.

## Reproduction

Use Node 26.10.0 and pnpm 12.5.1. Run `pnpm install --frozen-lockfile`, `pnpm test`, `pnpm typecheck`, `pnpm lint`, `pnpm build`, `pnpm db:local`, then `pnpm dev`. The Worker listens on `http://127.0.0.1:8787`. D1 and SQLite Durable Objects persist in the ignored `.wrangler/state` directory; preserve it across restarts and while a sandbox session exists. No remote Cloudflare account or resource is needed for these commands.

There is one package. `pnpm-workspace.yaml` contains only pnpm 12 dependency build permissions, with no workspace packages. It is package-manager configuration, not a monorepo. Build scripts are allowed only for esbuild/workerd; the optional core-js-pure postinstall is denied. Direct dependencies and the lockfile are pinned. Runtime type generation uses `--include-env false` and is regenerated by typecheck/build into an ignored file (the upstream generator emits trailing whitespace); application bindings are strictly typed in `src/worker/env.ts`.

Pinned core versions: Agents 0.28.1; MCP server/client 2.3.1; Wrangler 4.151.1; workerd 1.20261012.1 (transitive lock); Vitest 5.0.5; `@cloudflare/vitest-plugin` 1.4.4; Vite 8.3.4; TypeScript 5.9.3; React/React DOM 19.3.1; Tailwind 4.3.3; Base UI 1.9.0; Zod 4.6.7. The current plugin uses `cloudflareTest()` and per-file storage isolation. It does not export the old `fetchMock`; tests replace the outbound `fetch` boundary while retaining real Workerd DO/D1 and the actual MCP handler.

Sources checked during implementation: [Workers testing](https://developers.cloudflare.com/workers/testing/vitest-integration/write-your-first-test/), [test APIs](https://developers.cloudflare.com/workers/testing/vitest-integration/test-apis/), [DO class exports](https://developers.cloudflare.com/durable-objects/reference/durable-objects-migrations/), [Agents factory handler](https://developers.cloudflare.com/agents/model-context-protocol/apis/handler-api/), [Base UI Button](https://ui.shadcn.com/docs/components/base/button), npm package metadata and installed SDK declarations. ## Implemented path

The single Worker serves static assets, `/api/tools`, authenticated session open/status/activate/close and `/mcp`. It checks exact origin/Host, signed scoped bearer expiry, bounded bodies and repeated DO ownership. Two deterministic paid fixtures cost 20/35 cents. SQLite owns reservation, immutable fingerprint, result cache, usage ledger, close barrier, fixed payment operations and singleton settlement. Pending or unknown payment remains frozen; recovery reads provider resources instead of resending an ambiguous financial POST. Zero use selects void only. Positive use selects explicit final capture only.

A conditional D1 admission insert precedes the first financial request. A durable versioned outbox projects absolute snapshots with an atomic D1 batch; failed ACKs can replay. Jobs and watchdog alarms survive eviction, and an indexed scheduled scan can restore alarms. Wrangler does not automatically run cron triggers in local dev; the scan is exercised explicitly in runtime tests, while DO alarms are separate. The local adapter keeps credentials outside tool results and checks policy/human hooks before creating an order. `scripts/e2e-sandbox` additionally persists stable call/creation keys across process restarts.

The React screen is an English read-only M1 shell with a Base UI shadcn-style Button, tool prices and honest sandbox/AI labels. There is no merchant table yet; AG Grid Community is deferred to M4 and no Enterprise dependency exists. Browser DOM/visual inspection and real local routing were checked separately from automated runtime tests.

## Sandbox prepare / resume

The ignored `.dev.vars` must contain only server-side runtime credentials: `PAYPAL_CLIENT_ID`, `PAYPAL_CLIENT_SECRET`, `PAYPAL_MERCHANT_ID` and a random `OWNER_TOKEN_SIGNING_KEY` of at least 32 characters. Keep mode 0600. The first two may be loaded from the authorized external sandbox environment file; buyer email/password are not needed or copied. The configured 13-character sandbox Business merchant ID must match the app's account. OAuth success by itself does not establish this ID. Never put credentials in CLI arguments, browser storage, `VITE_*` variables, screenshots or tool results.

```sh
pnpm sandbox:setup
# Copies only server credentials; preserves the local signing key. Restart pnpm dev.
pnpm sandbox --prepare --evidence /absolute/private/evidence
# Human opens approve-url.txt and approves in PayPal; preparation does not do this.
pnpm sandbox --resume --evidence /absolute/private/evidence
# Two interactive 35-cent consent prompts; then 20+35+35, replay, close and independent GET checks.
# Alternatively, after the human wallet approval, explicitly consent to those fixed fixture calls:
pnpm sandbox --resume --approve-fixture-calls --evidence /absolute/private/evidence
pnpm sandbox --verify --evidence /absolute/private/evidence

# Separate zero-use path; separate human wallet approval is required.
pnpm sandbox --prepare --zero-use --evidence /absolute/private/evidence
pnpm sandbox --resume --zero-use --evidence /absolute/private/evidence
pnpm sandbox --verify --zero-use --evidence /absolute/private/evidence
```

`--approve-fixture-calls` is accepted only on the ordinary `--resume` path. It explicitly consents to this fixed 20+35+35-cent run, including both threshold prompts; it neither approves the wallet nor raises any price/budget cap. Without the flag, the two `yes` prompts still require a terminal. `--prepare` validates the independent order GET before writing an approval URL.

The script stores private state before open, uses the same creation key on retry, and never automatically replaces an expired/unknown session. Approval has a 30-minute deadline. If the human returns after expiry, inspect the old provider resources and deliberately prepare a new evidence directory/session; do not extend the old deadline. The script reissues a short-lived local bearer for the same private owner, without storing it in evidence. Resume requires the retained local database and signing key. `--verify` only reads. Provider GET verification checks one capture, 90 cents, USD, final flag and order/authorization relationship, or no captures and a VOIDED authorization on the zero-use branch. It does not claim a measured bank refund.

Settlement verification checks the exact currency and decimal total while allowing provider amount metadata such as `breakdown`. Comparing the entire amount object incorrectly rejected both completed sandbox orders. Verification also checks the exact three ledger entries, captured amount, settlement success/release evidence and authorization status against the independent provider GETs. A failed assertion does not authorize a replacement payment; use `--verify` with the existing evidence directory after diagnosing it. Neither verify command needs interactive consent.

## Evidence and remaining gates

`pnpm test` passed 101 tests in six files on 2026-10-18, covering domain and runtime/contract tests with synthetic provider responses, including amount-metadata acceptance and invalid-total/currency rejection. Typecheck, lint and build also passed. These are **local-runtime + mocked-provider** results, never real sandbox captures. Expected rejected DO RPCs may print allowlisted error codes from Workerd; the suite must still report zero unhandled test errors. `pnpm test:unit`, `pnpm test:workers` and `pnpm test:contract` select the three families.

Baseline mapping assertions are tagged T01–T41, P01–P08, M01–M08 in tests. Several baseline slots share one stronger scenario, and parameterized invalid budgets are kept individually. T03 proves exact 20×7 arithmetic and twenty actual SQLite reservations/ledger entries under a test-only seven-cent quote; the production catalog stays fixed at 20/35 cents. M05 currently proves the unimplemented merchant API is inaccessible; a working public demo projection remains M4. T41 proves actual local DO eviction, not deployed restart. M01 exercises the real SDK and policy adapter, but its browser approval/human responses are test hooks. These distinctions do not complete the full 57-behavior M2–M4 migration gate.

Additional local evidence covers ten concurrent reservations, duplicate in-flight calls, deferred execution versus close, late fenced completion, unknown unsafe reservation, lost capture/void responses, pending-to-completed reads, mismatched payment facts, stale outbox replay, D1 admission/projection outage, recovery scan, duplicate alarms, scoped/expired bearer, cross-owner requests and protocol mismatch rejection.

Both prepared orders were subsequently approved by the owner and resumed. Independent sandbox GET verification now passes for the existing 90-cent final capture and the separate zero-use void. The earlier `VERIFY_SETTLEMENT` failure was a verifier false negative caused by additional amount metadata, not a payment or ledger mismatch. Read-only SQLite inspection confirmed matching DO/D1 versions, states and amounts, one settlement per session and no undelivered outbox entries. An existing completed-call replay returned zero additional accrual with the snapshot and version unchanged. No replacement order or settlement was created during this repair; identifiers and detailed proofs remain only in private evidence.

The configured merchant ID was absent during the initial preparation run. After it was supplied, a running DO still observed the old binding set even though the local file contained it. A full restart of the actual Wrangler parent process restored the binding; the same creation key then prepared the original session. Configuration errors retain the allowlisted `PAYMENT_CONFIG_REQUIRED`/503 code across RPC, and the CLI reports a safe stage/code without assertion values.

The subsequent 19:47 KST owner authorization permitted the account-specific remote deployment described in [M1 remote preparation](M1-REMOTE.md). Remote pre-approval smoke/CPU evidence is available; paid execution/capture/void measurements still await separate buyer approval. The local benchmark sends 100 tools/list requests and 20 concurrent malformed requests. Wall-clock latency is not CPU. A macOS `ps` CPU delta across this repository's Workerd processes is only a coarse aggregate and cannot establish the Free 10 ms limit. The exact selected client is the local adapter/driver 0.1.0 with MCP client 2.3.1; an actual external AI host and model-driven run remain unverified and no LLM API was called.
