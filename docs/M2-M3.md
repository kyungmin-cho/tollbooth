They prove the verification API contract and fail-closed behavior, **not** genuine PayPal signatures. Alarm retry exhaustion is modeled by removing the platform alarm after a throwing handler, then restoring it through the real D1 scan; it is not an observed production retry sequence. ## Storage and operational recovery

DO schema version 2 is additive. Recovery counters/deadlines, provider cooldown, post-settlement review metadata and the verified inbox live in dedicated tables; existing calls, operations and singleton settlement retain their identities. D1 migration 0002 must precede deploying this build. Existing terminal sessions can be explicitly reprojected through the operator rebuild endpoint; rebuilding never creates a payment. An unknown create response with no recoverable order identity remains in review, rather than sending a new order POST.

`GET /api/operator/sessions/:id` returns safe DO state, immutable operation identities, settlement, jobs, retry counters and inbox/outbox counts. `POST .../:id/reconcile` reads PayPal resources and updates confirmed state; it never sends authorize/capture/void. `POST .../:id/rebuild` emits a fresh absolute projection from the DO. These routes require a short-lived separately scoped credential issued by the existing private signing authority; no public operator-token endpoint exists. No endpoint permits force-paid or arbitrary financial retry.

Refund/reversal notifications are review flags alongside historical captured gross; they do not rewrite usage, issue refunds or claim net revenue. Refund resources may carry their own ID: their validated sandbox capture reference is resolved to a known capture and checked by provider GET. Event-supplied URLs are never fetched. Minimal verified metadata and a body hash are retained; payer fields and original bodies are discarded.

## First-run remote verifier failure

The previous remote resume failures did not retain the failing assertion operands. D1 cannot be their direct source because the driver does not read D1. Two one-shot assumptions were present: immediate ACTIVE after activation and immediately converged independent PayPal order/authorization/capture views after DO settlement. The latter is reproduced for both positive and zero-use paths in Workers tests, with a terminal DO and an initially stale provider GET.

The driver now polls authoritative DO state during activation and retries only explicitly recognized not-ready provider evidence, with 31 attempts and a 2-second interval. Each network request has its own timeout; this is an attempt bound, not a strict 60-second wall-clock deadline. Contradictory totals, extra captures, foreign IDs and malformed evidence still fail immediately. Verify performs reads only; retries never repeat settlement POSTs. Safe diagnostics identify the verification stage without exposing operands. A second runtime regression covers a completed capture with a still-CREATED authorization GET: the DO now keeps reconciliation open until the authorization also confirms CAPTURED, instead of persisting inconsistent terminal metadata. This repairs the reproduced ordering defects; the precise historical failing field remains unproven because the original diagnostics omitted it.

Owner-authorized registration was completed on 2026-10-19 for the sandbox app below. The external environment and existing Worker secret now contain `PAYPAL_WEBHOOK_ID`. An unsigned POST returns 400 (fail closed). D1 ingress is DELIVERED for all six; each session DO has three APPLIED inbox entries. The production ingress requires verify-webhook-signature SUCCESS before insertion; raw signature/verifier response payloads are intentionally not persisted. Registration used GET before POST to avoid duplicates; no simulator signature claim is made. Configuration:

## Reproduction and approval handoff

Run `pnpm test`, `pnpm typecheck`, `pnpm lint`, `pnpm build`, `pnpm verify:secrets`. The existing dependency pins are unchanged. Real sandbox commands read PayPal credentials from the external runtime source; the private ignored runtime file supplies only the existing bearer signing key to the driver.

For new sessions at the current origin (never reuse origin-bound historical evidence), append `--origin https://tollbooth.arcsolve.workers.dev --evidence <new-private-evidence-directory>`. Run `pnpm sandbox --prepare` and separately `pnpm sandbox --prepare --zero-use`; canonical approval files are `approve-url.txt` and `zero-approve-url.txt`. Stop for human approval. Afterwards, run `pnpm sandbox --resume --approve-fixture-calls` and `pnpm sandbox --resume --zero-use`, then `pnpm sandbox --verify` and `pnpm sandbox --verify --zero-use`, each with those same origin/evidence arguments. The fixture flag consents to the fixed 90-cent run, not wallet approval. If the 30-minute application approval deadline elapsed, inspect the existing sessions before deliberately creating replacements; the script never silently replaces them.

Private evidence records test counts, exact commits, deployment version, order states, approval deadlines and commands. Browser ownership/bootstrap, single-use callback, merchant UI, genuine remote webhooks, paid-path CPU on this build, and actual AI remain distinct later gates.
